# oversight-rip

Code and results for "Efficient Scalable Oversight via Rewinding": rewindable interactive proofs (RIPs) for
scalable oversight. This repository contains our protocol, in which one prover answers the verifier's queries after being rewound
to a state it fixed before them, the measurements behind two results of Section 7 of the paper, and the
commands that regenerate them:

| In the paper | Shipped results | Regenerated by | Hardware for a full rerun |
|---|---|---|---|
| Table 1, Figure 1 and their text: the protocol on the MNIST circuits, 256 to 2^26 views, against direct evaluation | `results/mnist/` | [MNIST experiment](#mnist-experiment-table-1-and-figure-1) | one Graviton 4 core; 400 GB of memory at 2^26 views |
| Table 2 and its text: BLAKE3, the prover time of upstream Flock untouched against our protocol over GF(2^64), 2^22 to 2^34 witness bits | `results/blake3/` | [BLAKE3 experiment](#blake3-experiment-table-2) | one Graviton 4 core; 28 GiB of memory at 2^34 bits |

To check the paper against the shipped results, which takes seconds and needs only Python 3.9 or later:

```sh
python3 scripts/check_paper.py --paper section7.tex   # the LaTeX source of the paper's Section 7
```

It recomputes every number stated in the text of the two results and compares it with the paper's statement,
and compares Table 1, Table 2 and the coordinates of Figure 1, read from the paper's LaTeX source, row by row
with the tables regenerated from `results/`. It prints each comparison, then how many it made and what it did
not compare. It ends with `all figures match the paper` only when every table row, Figure 1 and every text
figure were compared and agree; without `--paper` the tables and Figure 1 are not compared.

## Reproducing the tables

After the [setup](#setup), one command runs every measurement behind Section 7's two results, prints the
regenerated tables and sets them against the paper:

```sh
bash scripts/reproduce_all.sh section7.tex      # the paper's Section 7 source, for the comparison; optional
```

As shipped it runs the two MNIST sizes whose bundles are in the repository and all seven BLAKE3 sizes: about
20 minutes on one Graviton 4 core. With every MNIST bundle installed ([Inputs](#inputs)) it reproduces all of
Table 1 and Figure 1 as well: about 8 hours more, on an `x8g.48xlarge` (3 TB of memory for the 2^26-view
circuit). Its two halves run separately too:

```sh
bash scripts/reproduce_mnist.sh                                  # Table 1 and Figure 1, every installed bundle
bash scripts/reproduce_blake3.sh                                 # Table 2, all seven sizes (aarch64 only)
bash scripts/reproduce_blake3.sh results-rerun/blake3 22 24 26   # Table 2's first three rows
```

All write to `results-rerun/` in the layout of `results/`, so the table scripts read a rerun exactly as they
read the shipped results, and `python3 scripts/check_paper.py --results results-rerun --paper section7.tex`
sets the rerun's table rows against the paper's for every size it holds (the text figures need every size).
The table scripts refuse a run that is incomplete, from another configuration or size, or whose protocol and
baseline read different inputs; delete `results-rerun/` between unrelated reruns. As shipped, the MNIST script runs the 256- and
1,024-view circuits, whose bundles are in the repository, in seconds; the other eight sizes need their
bundles installed first ([Inputs](#inputs)), and `bash scripts/reproduce_mnist.sh results-rerun/mnist 4096`
runs one size. The BLAKE3 script clones upstream Flock at the pinned revision and takes about 15 minutes for
all seven sizes on one Graviton 4 core, building included, with 28 GiB of memory at 2^34 bits. Both build first, pin to one core with `taskset` where it exists (`CORE`, default
4), and run one thread. Timings move with the CPU; verifier oracle queries, robustness and soundness
parameters reproduce exactly.

The prover's time in both tables is the sum of its two roles, which the measurements time separately. In the
MNIST measurements the main role sends all the prover's messages, including its answers to the verifier's
opening queries once they are sampled, and the answering role, the prover rewound before its one query,
independently rebuilds its fixed state from its own witness and answers, and the verifier checks that answer
against the main role's; summing the two counts that rebuild, so it overstates one rewinding prover's time.
In the BLAKE3 measurements the prover fixes each proof string's snapshot as it posts it, and answering only
reads those snapshots.

## Contents

- `crates/`: the Rust implementation. `rmip-field` (binary-field arithmetic), `rmip-frontend` (oracle
  circuits, among them the MNIST majority circuits), `rmip-iop` and `rmip-packed` (the encoded-witness IOP,
  with its zerocheck, lincheck and ring switching over GF(2^64)), `rmip-backend-ladder` and the other
  backends (the Ligero-style opening with pins), `rmip-mip` and `rmip-mip-prover` (the compilation and
  the prover's two roles: the main messages, and the answers given after rewinding), `rmip-holo`, `rmip-opt`, `rmip-demo` (the measured execution of the MNIST
  experiment), `rmip-bench` (the `mnist_survey` binary) and `rmip-flock` (Flock's IOP compiled into our
  protocol over GF(2^64), the prover rewound before each query).
- `vendor/flock/`: Flock, vendored as the base of our compilation, with our GF(2^64) port.
  `vendor/flock/PROVENANCE.md` names the upstream revision and lists every change. Table 2's Flock numbers come
  from that upstream revision, untouched, not from this copy.
- `tools/mnist/`: the Python pipeline that builds the MNIST circuits' input bundles from the frozen
  classifier (`train_sparse_judge.py` defines the classifier's architecture, which the pipeline loads;
  training is not part of the reproduction). `tools/mnist-direct-eval/`: direct evaluation of the circuits, the baseline of Table 1.
- `benchmarks/checkpoints/sparse_judge_v1.pt`: the classifier, pinned by its SHA-256;
  `benchmarks/artifacts/sparse_judge_accuracy.json`, its measured accuracy on random six-pixel views of the
  whole test set (59.4%, the paper's figure), which `scripts/check_paper.py` reads.
  `benchmarks/mnist-test/artifacts/R<views>/`: for each circuit size, the manifest with the input bundle's
  hash, the configuration and the per-image robustness certificates; the bundles themselves for 256 and
  1,024 views.
- `results/`: the measured ledgers and logs. `scripts/`: the table, generation and check scripts.

## Setup

Rust 1.98.0, pinned in `rust-toolchain.toml`. The field arithmetic needs the hardware carry-less multiply,
so build with native code generation:

```sh
export RUSTFLAGS="-C target-cpu=native"
cargo build --release --locked
cargo build --release --locked --manifest-path tools/mnist-direct-eval/Cargo.toml
cargo test --release --locked                                    # the test suite, a few minutes
```

On x86-64 the multiply needs `-C target-feature=+pclmulqdq,+sse4.1` if `target-cpu=native` does not imply
it. The BLAKE3 experiment runs Flock's AG-skip prover, which Flock provides for aarch64 only; on x86-64
those tests and fixtures are compiled out.

Python 3.9 or later. Building bundles also needs `torch==2.8.0` (CPU build), `numpy==2.0.2` and the MNIST
test set:

```sh
mkdir -p benchmarks/data && cd benchmarks/data
for f in t10k-images-idx3-ubyte t10k-labels-idx1-ubyte; do
  curl -fsSLO https://ossci-datasets.s3.amazonaws.com/mnist/$f.gz && gunzip -k $f.gz
done
shasum -a 256 t10k-images-idx3-ubyte t10k-labels-idx1-ubyte; cd ../..
# 0fa7898d509279e482958e8ce81c8e77db3f2f8254e26661ceb7762c4d494ce7  t10k-images-idx3-ubyte
# ff7bcfd416de33731a308c3f266cc351222c34898ecbeaf847f06e48f7ec33f2  t10k-labels-idx1-ubyte
```

All timings in the paper were taken on AWS Graviton 4 cores (Neoverse V2), one single-threaded process
pinned to one core (`taskset -c 4`, `RAYON_NUM_THREADS=1`), with transparent huge pages enabled:

```sh
echo always | sudo tee /sys/kernel/mm/transparent_hugepage/enabled /sys/kernel/mm/transparent_hugepage/defrag
```

Absolute times depend on the CPU; every ratio in the paper compares measurements on the same core type. A
rerun moves timings by a few percent. Protocol coins are fresh operating-system randomness, so transcripts
differ between runs; acceptance, oracle-query counts and soundness parameters are fixed by the bundle and
the circuit size.

## MNIST experiment (Table 1 and Figure 1)

### Inputs

A bundle holds, for the selected test images, the registered six-pixel views of each image and the
classifier's answer on every view, with each image's exact robustness certificate. The 50 images are fixed
(`SELECTED_IMAGE_IDS` in `tools/mnist/survey_sparse.py`): the first 50 test images whose 256-view circuit
accepts the correct digit with robustness at least 1/8. At 2^24 views image 40, and at 2^26 views images
31, 40 and 57, have fewer distinct six-pixel views than the circuit needs and are omitted, so those sizes
have 49 and 47 images.

The 256- and 1,024-view bundles are in this repository. All ten are archived at Zenodo,
https://doi.org/10.5281/zenodo.23604984 (gzipped, under 0.1 GB each up to 65,536 views, then 0.17, 0.68,
2.1, 8.5 and 32.7 GB; 44 GB in all, with the manifests and a `SHA256SUMS` file), or can be regenerated. A
downloaded bundle must have its manifest's hash; for one size, with `R` the number of views:

```sh
A=benchmarks/mnist-test/artifacts
sha() { python3 -c "import json; print(json.load(open('$A/R$1/manifest.json'))['artifacts']['selected.json']['sha256'])"; }
curl -fL -o mnist-bundle-R$R.json.gz "https://zenodo.org/records/23604984/files/mnist-bundle-R$R.json.gz?download=1"
gunzip -c mnist-bundle-R$R.json.gz > $A/R$R/selected.json; shasum -a 256 $A/R$R/selected.json; sha $R
```

Generation is deterministic: the views are drawn with a fixed per-image seed and the classifier runs with
deterministic algorithms. Up to 1,048,576 views, one process per size, then `check_bundle.py`:

```sh
python3 tools/mnist/survey_sparse.py --views 4096 --threads 4      # writes benchmarks/mnist-test/generated/R4096
python3 scripts/check_bundle.py 4096 benchmarks/mnist-test/generated/R4096 --install
```

A bundle records the hashes of the scripts that generated it, and the published bundles up to 1,048,576
views were generated by two earlier revisions of `survey_sparse.py`. `check_bundle.py` therefore checks
that every vote of every image is identical, puts the recorded script hashes back, checks that the result
has the manifest's hash, and only then installs it.

This takes about 1.5, 5.5 and 23 minutes at 4,096, 16,384 and 65,536 views with four threads, and about 8
and 31 minutes at 262,144 and 1,048,576 views spread over 64 x86 cores. The three largest sizes split the
work into stages so that many single-threaded workers share the classifier evaluations, then merge the
per-image shards; the merged bundle is byte-identical to a single-process run:

```sh
python3 scripts/generate_large_bundle.py --views 4194304 --image-ids <ids for this machine> --workers 190
python3 tools/mnist/survey_sparse.py --views 4194304 --image-ids <all ids> --merge <shard dirs> \
  --output benchmarks/mnist-test/generated/R4194304
python3 scripts/check_bundle.py 4194304 benchmarks/mnist-test/generated/R4194304 --install
```

The published bundles took 25 minutes, 1.6 hours and 6.4 hours of wall time at 2^22, 2^24 and 2^26 views
on two `c7i.48xlarge` and one `c7i.24xlarge` (about 200, 780 and 3,000 vCPU-hours). At 2^26 each mask
process needs about 25 GB, and the merges of the shards peak at 57, 223 and 855 GiB (`results/mnist/logs/merge-*.log`).

### Running the protocol and direct evaluation

For one circuit size `R` with `N` images (50, or 49 at 2^24 and 47 at 2^26):

```sh
taskset -c 4 target/release/mnist_survey --mode protocol --backend ladder --body packed64 \
  --soundness single-shot-40 --depth 0 --images N \
  --selection $A/R$R/selected.json --expected-selection-sha256 "$(sha $R)" \
  --output-dir results-rerun/mnist/R$R
taskset -c 4 tools/mnist-direct-eval/target/release/mnist-direct-eval --images N --probes 9 \
  --selection $A/R$R/selected.json --expected-selection-sha256 "$(sha $R)" \
  --output results-rerun/mnist/direct-eval-R$R.json
```

`mnist_survey` runs the complete protocol once per image at soundness error 2^-40, with no repetitions,
and times the prover's two roles and the verifier separately: the main role (witness generation and every
oracle lookup included), the answering role (its own witness and the reconstruction of the proof strings
included) and the verifier (its own oracle calls included); Table 1's prover time is the sum of the two roles
per image. Before the timers start, the harness builds the circuit for the image and compiles each view's
oracle query into a word from the circuit (`PackedStatement::with_query_plan`); both roles read those words,
and building them is not timed. It writes one ledger with every image's measurements, protocol parameters and error terms.
Oracle lookups are counted, not recorded; `--record-lookups` keeps a per-lookup log for diagnosis, at a
cost of about 125 ns per view inside the main role's timer on a Graviton 4 core, so it must stay off when timing. `mnist-direct-eval` times the direct
loop (an in-order scan of the classifier's answers counting the accepted label's votes, then the threshold
comparison; the best of nine batched probes) on the same core. Its JSON also records two other timings the
paper does not use, the same loop reading the answers through an index list and a gate-by-gate interpreter.

| Views | Survey wall time (all images) | Survey peak memory | Direct evaluation |
|---|---|---|---|
| 256 to 65,536 | seconds | under 0.5 GiB | seconds |
| 262,144 / 1,048,576 | about 1 / 2 min | 1.5 / 6.2 GiB | under 1 / 3 min |
| 2^22 / 2^24 / 2^26 | 9 / 35 / 137 min | 25 / 97 / 370 GiB | 12 / 50 / 203 min |

At the three largest sizes most of the time goes to constructing each image's case from the bundle (the
circuit and its witness trace, about 57% of the wall time) and to loading the JSON bundle; the protocol
itself is a small share. The paper's runs used one `x8g.48xlarge` (Graviton 4, 3 TB) for all ten sizes.

```sh
python3 scripts/make_mnist_table.py results/mnist          # Table 1 as LaTeX, Figure 1's coordinates, every row
python3 scripts/make_mnist_table.py results-rerun/mnist    # the same from a rerun
```

## BLAKE3 experiment (Table 2)

Flock's IOP proves batches of BLAKE3 compressions; `bits` is the witness size, `2^(bits − 14)` compressions.
Table 2 compares the time of two provers on the same statements; the verifiers' times and the proof and
message sizes are measured too and stay in the logs, and the text reports our compilation's error:

- **Flock, untouched**: upstream Flock (https://github.com/succinctlabs/flock) at revision
  `b684b1258e4b1f202bec24afd660ace851b09e5e`, built with its own configuration and run with its own benchmark
  (`crates/flock-prover/benches/blake3_proof.rs`: one warm-up, three timed proofs, then one verification and
  the proof size), as it ships: GF(2^128), Merkle commitments and Fiat-Shamir, its `Fast` profile at a 128-bit
  security target, met in part with proof-of-work grinding. Its timer covers witness generation and proving
  and stops before the proof is serialized.
- **Ours**: our compilation of Flock's IOP over GF(2^64) (`reset_cost` in `crates/rmip-flock/tests/reset.rs`,
  one warm-up and three measured executions) at our 40-bit interactive parameter setting, an error ledger we
  added to the vendored copy; upstream Flock has no such setting and no 64-bit field. One rewinding prover runs
  Flock's prover with the commitments removed. When it posts each proof string it fixes its own snapshot of it
  from the coefficients it posts, before any later coin: the first layers of the encoding applied to every row.
  After its messages it answers each query from that snapshot, rewound before each query, by finishing the
  remaining layers along the requested row only; nothing is recomputed, and every answer equals the row of the
  complete encoding. The verifier runs Flock's verifier on those rows. The prover's time is its messages, the
  snapshots included, plus its answers, per measured execution; witness generation and the serialization of
  its messages included (the finishing step that serializes them takes under 0.3 ms in every recorded run; the
  logs' `finish_ms`), setup excluded. Most coins are
  drawn in GF(2^64); Ligerito's fold and sumcheck challenges are drawn in GF(2^128).

`bash scripts/reproduce_blake3.sh` runs both at every size. By hand, for one size, with `LB = bits − 14`:

```sh
git clone https://github.com/succinctlabs/flock flock-upstream
git -C flock-upstream checkout b684b1258e4b1f202bec24afd660ace851b09e5e
(cd flock-upstream && RAYON_NUM_THREADS=1 BLAKE3_LOG2S=$LB BLAKE3_RUNS=3 taskset -c 4 \
  cargo bench --locked --bench blake3_proof)                                                 # Flock
RUSTFLAGS="-C target-cpu=native" RAYON_NUM_THREADS=1 RMIP_MIP_LOG_BLOCKS=$LB taskset -c 4 \
  cargo test --release --locked -p rmip-flock --test reset reset_cost -- --ignored --exact --nocapture --test-threads=1   # ours
```

`RAYON_NUM_THREADS=1` matters beyond rayon's global pool: Flock's NTT moves transforms of 64 MB or more onto
a separate all-core pool that only this variable limits.

The results here were measured on two `x8g.4xlarge` machines (Graviton 4) on 2026-10-21, each run on one
core: Flock in about 7 minutes for all seven sizes, ours in about 2. Memory stays under 4 GB up to 2^30 bits;
at 2^34 Flock peaks at 28 GiB and ours at 20 GiB. Then:

```sh
python3 scripts/make_blake3_table.py results/blake3 --latex          # Table 2's rows, error terms as comments
python3 scripts/make_blake3_table.py results/blake3                  # the prover comparison and our error, as Markdown
```

The error bound of our compilation is its IOP's error at our 40-bit setting, 2^-42.4 to 2^-42.9 at these
sizes: the sum of the IOP's query and algebraic terms, whose statistical composition the vendored interactive
parameter code states as an assumption.

## What this copy is

The results were produced from the full development repository. This copy differs from it in what was left
out (development notes, other experiments, code that neither result uses, and upstream Flock's own benchmark
notes, documentation, scripts, README, GPU prover interface, benchmarks, debugging binaries and examples;
its tests remain and pass with `cargo test` inside `vendor/flock`, in Flock's default GF(2^128)
configuration; under the GF(2^64) feature our port added, 24 of its test fixtures were not ported and do not
compile, and the port is tested by `flock-field`'s unit tests and by `rmip-flock`'s tests instead), in
comments removed from
our Rust code, and in fixes that touch no timed code path (input validation, report fields and
architecture guards). The encoder of `rmip-flock` ships as its own module, `encoder`, with error type
`EncodeError`; in the development tree it shares a file, `pinning.rs`, with a pinned variant of the
compilation that this copy leaves out. `rmip-flock` ships only its GF(2^64) build; the development tree also
builds it over Flock's GF(2^128). The `source_fingerprint` in each ledger refers to the measured tree, and
the ledgers and logs, which are the measurement records, keep the measuring machines' paths and the names
of internal notes as they were written. Files vendored
from Flock and the GHASH arithmetic keep their upstream license headers, and the `PROVENANCE.md` next to
them lists every change.
